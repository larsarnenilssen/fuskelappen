# 099 – Dependabot, Node 24 og overvåking av jukselappen.no

**Kontekst:** Gjennomgangen 09.10.2026 fant at ingenting holder avhengighetene og Node oppdatert (Node 22 får ikke oppdateringer etter 30.04.2027), at ingen sjekker at jukselappen.no svarer eller at en publisering faktisk kom ut, og at varslene sa «går ofte over av seg selv» også når en kilde hadde endret format (kontrollsak #92: «Cannot read properties of undefined»).

**Valg:**
- **Dependabot** (`.github/dependabot.yml`): npm og GitHub Actions én gang i måneden.
  - Minor- og patch-oppdateringer kommer samlet i tre PR-er: én for utviklingspakkene, én for produksjonspakkene og én for Actions.
  - Nye hovedversjoner av npm-pakker kommer hver for seg. Høyst fire åpne PR-er for npm og to for Actions.
  - `@playwright/test` kommer for seg, fordi bildet i `ci.yml` må ha samme versjon (testet). Claude endrer bildet i samme PR.
  - **Slik behandles de:** som andre PR-er. Claude fletter når CI er grønn og det ikke er konflikter (eier 01.10.2026). En ny hovedversjon vurderes først: Claude leser endringene, retter det som må rettes i samme PR, og spør eier hvis noe brukerne merker endres. En PR som ikke kan rettes, lukkes med en kommentar om hvorfor.
- **Node 24** (LTS) i `.nvmrc` og `engines`. Lint, typesjekk, tester og bygg er kjørt med Node 24.21.0. `@types/node` står på 22 til Dependabot foreslår 24.
- **Røyktest etter publisering:** Siste steg i «Publiser» henter forsiden og `versjon.json` fra adressen GitHub Pages oppgir, med en ny parameter hver gang, så svaret ikke kommer fra mellomlageret. Forsiden må være byte for byte den samme som i bygget, og versjonsnummeret det samme som i bygget. Det prøves i fem minutter. Feiler det, feiler publiseringen, og saken om feil i automatikken kommer (avgjørelse 085): fra arbeidsflyten som kalte publiseringen, eller fra «Publiser» selv når den er startet for seg (tag, testversjon eller for hånd).
- **Oppetid:** Arbeidsflyten Nyheter, som går hver time, sjekker også at jukselappen.no svarer. Svarer den ikke, prøves det igjen etter ti minutter. Først når den ikke har svart to ganger på rad, kommer saken «Feil i automatikken: Oppetid». Den lukkes når siden svarer igjen. Sjekken får feile uten at kjøringen feiler, så GitHub ikke sender sin egen e-post i tillegg. To forsøk i samme kjøring er valgt i stedet for to kjøringer på rad, fordi GitHub kan starte kjøringene timer for sent, og fordi det ikke trenger noe lagret mellom kjøringene.
- **Nettfeil eller formatendring** (`scripts/varsel/feiltype.ts`): En feilmelding som ligner en programfeil eller et uventet svar (TypeError, «Cannot read properties», skjemafeil, «ser ikke ut som ventet», «Fant ikke innholdet», 404) regnes som en formatendring. Nett, tidsavbrudd, 429 og 5xx regnes som forbigående. I kontrollsaken står kildene med formatendring for seg, med «Kilden ser ut til å ha endret format – send lenken til denne saken til Claude.» Det samme står i saken om feil i automatikken for Kildesjekk og Nyheter når loggen ligner en programfeil. Det andre står som før.

**Konsekvens:** Det kommer noen få PR-er fra Dependabot i måneden. Eier må gi Dependabot lov i innstillingene (se rapporten til eier). En publisering som ikke kommer ut, eller en side som er nede, gir én e-post, ikke én per time. Oppetiden sjekkes bare så ofte som GitHub starter kjøringene. En ekstern vakt ville vært mer presis, men er en tjeneste utenfor GitHub som eier må velge selv.

**Endret 09.10.2026:** Nye hovedversjoner av `@types/node` foreslås ikke. Typene følger Node-versjonen appen bruker (`.nvmrc`), og endres sammen med den.
